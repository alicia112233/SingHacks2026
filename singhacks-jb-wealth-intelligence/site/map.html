Step 1 · Client records

Everything starts from the client's own record

TESSERA reads what the bank already holds about a client. This data is confidential (C3 to C4) and never leaves the bank.

C3–C4 client dataRead by code only

Goes in

Clients, portfolios, holdings, instruments, mandates, commitments, credit facilities, planned cash needs, and the event log with RM notes.

Comes out

One joined view per client: what they said they want, what they hold, and what they owe or need soon.

  • Structured notes and funds are looked through to their underlying holdings, so a sector bet inside a note still counts.
  • Stated goals come from the client's own words: source of wealth, objectives and RM notes.
  • No model reads this data to find a problem. Finding contradictions is arithmetic on holdings.

In the demo: synthetic clients from the Julius Bär SingHacks case dataset (data/*.csv).

Step 2 · Market news

Public headlines, refreshed on a schedule

TESSERA pulls financial headlines from public feeds. This is public data (C1 to C2), so it is safe to send outside the bank.

C1–C2 public data

Goes in

RSS feeds from Yahoo Finance, CNBC and The Business Times, plus optional Google News searches set by the bank.

Comes out

A list of events, each with a headline, publisher and date. Nothing about any client.

  • Each refresh keeps new events and skips ones already stored.
  • Extra feeds can be added by configuration, with no code change.

Feeds are set in TESSERA_NEWS_FEEDS.

Step 3 · External models triage headlines

Three public models vote on each headline

External models only ever see public headlines. They decide whether a headline matters for wealth clients, which topics it touches, and how severe it is.

Public data onlyExternal AI

Sent to each model

Headline text, publisher and date. Nothing else.

Comes back

Relevant or not, topics (for example energy, shipping, rates) and a severity.

  • Three models answer independently: GPT-5.4, Claude Sonnet 4.6 and Gemini 3.7 Flash.
  • Relevance and topics go by majority vote. Severity is the median of the three.
  • Each refresh triages the latest 60 events. If no model answers, fixed keyword rules decide instead.
  • News can add at most 8 points to a client's urgency score.

Switched on with TESSERA_NEWS_TRIAGE_ENABLED; models set in TESSERA_NEWS_MODELS.

Step 4 · Code detects and scores

Code finds the contradiction and ranks the client

Deterministic code compares what each client said with what they hold, then scores how urgent it is. No client is named in the rules, so a new client is checked the same way on day one.

Step 5 · In-house model reviews actions

The bank's own model checks each action from three angles

Proposed actions use client data, so only a model the bank runs itself reviews them. It can lower confidence in an action, never raise it.

In-house AIInside the bank
AngleAsks
Suitability and complianceDoes the action fit the mandate and the rules?
Client fitDoes it match what this client said they want?
Evidence qualityIs every claim backed by the record?
  • Final score is the lower of the code's score and the median of the three angles.
  • If the angles are more than 20 points apart, the result is capped at 69.
  • If any angle blocks the action, the result is capped at 49, and the RM can't approve it.
  • The packet is de-identified and checked for leaks first. The RM can open “What the model saw”.

In the demo, a labelled stand-in plays the in-house model. In production, TESSERA_INHOUSE_URL points at the bank's own model server.

Example from the demo

Angles scored 78, 74 and 82 (median 78). The code's score was 65.

Step 6 · The RM decides

Nothing reaches a client without the RM

The RM gets a short brief and three choices. TESSERA prepares the conversation; the RM has it.

Human decision
ChoiceRule
ApproveRM states the action taken (at least 10 characters). Blocked actions can't be approved.
EditRM writes the revised wording.
DismissRM can ask for an alternative action instead.

Step 7 · Ledger

Every decision is written down and never overwritten

Each approve, edit or dismiss is a new record. The current state is rebuilt from the full history, so compliance can see who decided what, when, and on what evidence.

Append-onlyInside the bank

Each record holds

Client, action title, decision, the RM's note, who decided, time, and the recommendation version.

Stored in

A local file in development. A Postgres table in production.

  • Records are only added. A change of mind is a new record, not an edit.
  • A dismissed action stays visible in the history with its alternative.

Code: tessera/services.py, tessera/review_state.py.
